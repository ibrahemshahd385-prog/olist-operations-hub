# شرح Module 1: الفواتير والطلبات

الملف ده معمول عشانك انتي يا شهد. الهدف إنك تفهمي كل جزء وتقدري تشرحيه وتدافعي عنه قدام المقيّم. اقريه وانتي فاتحة الكود جنبك.

---

## 1. الفكرة الكبيرة: ليه نبدأ من الفاتورة؟

- **Olist النهارده ERP-first:** حسب مقال Startups (أكتوبر 2026)، كل عميل جديد بيدخل Olist عن طريق الـ ERP بتاعها (Tiny، اشترتها سنة 2021). الـ ERP هو المكان اللي البائع بيسجل فيه البيعة ويطلع الفاتورة، وكل حاجة تانية مبنية فوقه: ربط الماركت بليسز، الدفع، التمويل (Credit)، والمساعد الذكي Lis على واتساب.
- **الفاتورة في البرازيل خطوة قانونية:** أي طلب بيتشحن لازم يطلع له **NF-e** (فاتورة إلكترونية) متوافق عليها، والنسخة المطبوعة منها اسمها **DANFE** ولازم تمشي مع الشحنة.
- عشان كده لما المنتور قال "سيستم من أول تسجيل الفاتورة"، الترجمة العملية هي **رحلة الطلب كاملة (Order-to-Cash)**: تسجيل البيعة ← الدفع ← تجهيز البائع ← الفاتورة ← شركة الشحن ← التوصيل ← التقييم.

**جملة تقوليها للمقيّم:** "بدأت من الفاتورة لأن ده بالظبط مدخل Olist لعملائها النهارده، ولأن في البرازيل مفيش شحن من غير NF-e."

## 2. رحلة الطلب (State Machine)

```
created → approved → processing → invoiced → shipped → delivered
   │          │           │            │
   └──────────┴───────────┴────────────┴──→ canceled
              └───────────┴───────────────→ unavailable
```

**جبت الترتيب ده منين؟** الداتا فيها 8 حالات. بصّيت كل حالة عندها أنهي timestamps متملية:
- `invoiced` و `processing`: عندهم `approved_at` بس، يعني الدفع اتأكد والطلب لسه مخرجش لشركة الشحن.
- `shipped`: عنده `delivered_carrier_date`، يعني الطلب اتسلم لشركة الشحن.
- `delivered`: عنده كل التواريخ.

**يعني إيه State Machine؟** كل زرار (action) مسموح بيه من حالات معينة بس. مثلاً زرار "Hand over to carrier" مش موجود أصلاً غير لما الطلب يبقى `invoiced`، فمستحيل طلب يتشحن من غير فاتورة. الكود في `backend/app/services/workflow.py` جوه dictionary اسمه `ACTIONS`.

### القواعد، وكل قاعدة وراها إيه

| القاعدة | الدليل |
|---|---|
| الدفع بالكارت بيتأكد على طول، والبوليتو (Boleto) بيستنى | الوقت الوسيط (median) للموافقة: **0.3 ساعة** للكارت و**29 ساعة** للبوليتو. البوليتو ورقة دفع العميل لازم يروح يدفعها في البنك أو الأبليكيشن. |
| التقسيط (Parcelamento) للكارت بس، من 1 لـ 24 قسط | في الداتا الكارت بس اللي فيه أكتر من قسط، و**67%** من مدفوعات الكارت متقسطة. |
| مجموع المدفوعات لازم يساوي إجمالي الطلب | **99.7%** من الطلبات القديمة بتطابق (المنتجات + الشحن) بالسنت. |
| فاتورة لكل بائع في الطلب | فيه **1,278** طلب فيهم أكتر من بائع، وكل بائع شركة مستقلة قانونياً وبيطلع فاتورته. |
| ممنوع الشحن من غير فاتورة | قاعدة برازيلية: الـ DANFE لازم تمشي مع الشحنة. |
| إلغاء الفاتورة مسموح خلال 24 ساعة بس | ده الحد العام لإلغاء الـ NF-e. بعد كده البائع محتاج يطلع فاتورة مرتجع (nota de devolução)، فالسيستم بيمنع الإلغاء ويقول السبب. |
| تحذير لما الشحن يبقى أغلى من المنتج | **4,124** منتج في الداتا حصل معاهم كده (من Task 1). |
| الطلبات القديمة read-only | عشان التحليل يفضل صادق. الطلبات الجديدة `source = 'system'` والقديمة `source = 'historical'`. |

## 3. الداتابيز

ملف الجداول: `backend/app/schema.sql`. اللي بيبنيها: `backend/scripts/build_database.py`.

### الجداول الأصلية (9)
سبتهم بنفس الأسماء وأسماء الأعمدة، عشان أي رقم يترجع للداتا الأصلية. التغيير الوحيد تصحيح الغلطة الإملائية `lenght` لـ `length`.

### نقطتين لازم تفهميهم كويس
1. **`customer_id` مش هو العميل.** Olist بتدي كل طلب `customer_id` جديد، والعميل الحقيقي هو `customer_unique_id` (96,096 شخص لـ 99,441 طلب). عشان كده لما بنسجل طلب لعميل راجع، بنعمل صف جديد في `customers` بـ `customer_id` جديد بس نفس الـ `customer_unique_id`. كده مشيت على نفس نظام Olist.
2. **كل وحدة مبيعة صف لوحدها.** لو العميل اشترى 3 قطع من نفس المنتج، الداتا بتسجلهم 3 صفوف (`order_item_id` = 1، 2، 3). السيستم بيعمل نفس الحاجة، وفي الشاشة بنجمّعهم تاني ونعرضهم كـ "Qty 3".

### الجداول الجديدة (اللي الداتا مكانتش فيها)
- **`invoices`:** فاتورة لكل (طلب + بائع). فيها الرقم المتسلسل، والمفتاح اللي 44 رقم، والحالة (authorized / canceled).
- **`order_events`:** سجل لكل تغيير حالة (إمتى حصل + ملاحظة). أي سيستم تشغيلي حقيقي لازم يبقى فيه audit trail.
- **`ref_state_delivery`:** لكل ولاية: Olist كانت بتوعد بكام يوم، والتوصيل الفعلي أخد كام يوم.

### قواعد الداتابيز نفسها بتحميها
في `schema.sql` فيه `UNIQUE INDEX`:
- بائع واحد ميقدرش يبقى عنده فاتورتين شغالين لنفس الطلب.
- رقم الفاتورة ميتكررش لنفس البائع.

يعني حتى لو حصل bug في الكود، الداتابيز هترفض.

### تنضيف الداتا
- الـ zip prefix يفضل نص: `01037` لو اتحول رقم هيبقى `1037` وده غلط.
- الـ geolocation: مليون نقطة اتحولوا لنقطة واحدة لكل zip (الـ median)، وشلت 42 نقطة برا حدود البرازيل.
- `review_id` مش unique في الداتا الأصلية، فاستخدمت الـ rowid.
- ملاحظة مهمة: ملف `order_items` اللي اتدالنا **مفيهوش عمود `shipping_limit_date`**، اللي موجود في نسخة Kaggle الأصلية. خدي بالك منها لو حد سألك.

## 4. الـ Backend: الطبقات

```
Request  →  routers/   (بيقرا الطلب ويرجع الرد بس)
         →  services/  (كل القواعد هنا)
         →  db.py + SQL
```

**ليه الفصل ده؟** الـ services مش عارفة حاجة عن HTTP، فممكن نختبرها لوحدها (وده اللي التيستات بتعمله). ولو بكرة عملنا شاشة موبايل أو بوت واتساب، نفس الـ services تشتغل معاهم.

**الأخطاء:** الـ services بترمي 3 أنواع أخطاء (`errors.py`)، و`main.py` بيحولهم لـ HTTP في مكان واحد:
- `NotFoundError` ← 404
- `BusinessRuleError` ← 409 (الطلب سليم بس قاعدة بتمنعه، زي إنك تشحني من غير فاتورة)
- `ValidationFailed` ← 422 (الداتا غلط، وبيرجع كل المشاكل مرة واحدة)

**ليه SQL عادي من غير ORM؟** كل query مكتوبة قدامك وتقدري تقريها وتشرحيها، ومفيش حاجة زيادة نسطّبها.

### مثال: طلب جديد بيمشي في الكود إزاي
1. الواجهة تبعت `POST /api/orders`.
2. `routers/orders.py`: الـ Pydantic (`schemas.py`) بيتأكد من الأنواع (السعر أكبر من صفر، الولاية موجودة، الـ zip 5 أرقام).
3. `services/orders.py` ← `create_order`:
   - يتأكد إن العميل والمنتجات والبائعين موجودين.
   - يتأكد إن التقسيط للكارت بس، وإن المدفوعات = الإجمالي.
   - يحسب ميعاد التوصيل الموعود من `ref_state_delivery`.
   - يسجل كل حاجة في **transaction واحدة** (`with conn:`)، يعني يا كله يتسجل يا ولا حاجة.
   - لو الدفع كله فوري (كارت/فاوتشر) يحول الطلب لـ `approved` على طول.
4. يرجع رقم الطلب والتحذيرات.

## 5. مفتاح الـ NF-e (44 رقم)

الكود في `services/invoices.py`.

```
35 2610 64861735452085 55 001 000000001 1 39190039 3
│  │    │              │  │   │         │ │        └ رقم التحقق (DV)
│  │    │              │  │   │         │ └ كود عشوائي (8)
│  │    │              │  │   │         └ نوع الإصدار (1 = عادي)
│  │    │              │  │   └ رقم الفاتورة (9)
│  │    │              │  └ السيريز (3)
│  │    │              └ الموديل (55 = NF-e)
│  │    └ CNPJ البائع (14)
│  └ السنة والشهر
└ كود الولاية (35 = ساو باولو)
```

**رقم التحقق (Módulo 11):** نضرب كل رقم من الـ 43 في وزن (2، 3، 4 ... 9 وبعدين نرجع لـ 2) من اليمين للشمال، ونجمع. لو باقي القسمة على 11 هو 0 أو 1 يبقى الـ DV = 0، غير كده الـ DV = 11 ناقص الباقي.

مثال صغير: لو كل الأرقام أصفار وآخر رقم 5 ← المجموع 5×2 = 10 ← الباقي 10 ← DV = 11 − 10 = **1**.

**الباركود:** في صفحة الـ DANFE فيه باركود Code 128 بيشفّر المفتاح، زي الفواتير الحقيقية. اتأكدت إن الجدول بتاعه مطابق لمكتبة reportlab رمز رمز، وإن الـ checksum بيطلع نفس الرقم.

**الـ CNPJ:** الداتا مخفية الهوية، فكل بائع واخد رقم وهمي ثابت مطلوع من الـ seller_id. والفاتورة مكتوب عليها **SEM VALOR FISCAL** (من غير قيمة ضريبية)، زي فواتير بيئة الاختبار في البرازيل بالظبط، لأننا مش بنبعت حاجة لـ SEFAZ (مصلحة الضرايب).

## 6. الواجهة (React)

| الشاشة | الملف | بتعمل إيه |
|---|---|---|
| الطلبات | `pages/OrdersPage.jsx` | طابور الشغل (مستني دفع ← يتجهز ← يتفوتر ← يتشحن ← في الطريق) + كل الطلبات بفلاتر |
| تسجيل طلب | `pages/NewOrderPage.jsx` | عميل ← منتجات من كتالوج البائع الحقيقي ← دفع، وملخص بيتحدث وانتي بتكتبي |

- **الواجهة بتتأكد والـ API بيتأكد تاني.** الواجهة للسرعة وتجربة المستخدم، والـ API هو المرجع، لأن أي حد ممكن يبعت request من غير الواجهة.

## 7. أسئلة متوقعة من المقيّم

**س: ليه مستخدمتيش ميعاد التوصيل الحقيقي بتاع Olist؟**
ج: استخدمته فعلاً في Module 1 عن قصد: السيستم بيوعد بنفس اللي Olist كانت بتوعد بيه. بس الداتا بتقول إن Olist كانت بتوعد بـ 23 يوم (median) والتوصيل الفعلي 10 أيام، و74% من الطلبات وصلت قبل الميعاد بأكتر من أسبوع. ميعاد طويل بالشكل ده ممكن يخلي العميل يلغي الشراء. Module 2 هيبدل الوعد ده بمودل.

**س: إيه اللي حقيقي وإيه اللي محاكاة؟**
ج: الداتا والقواعد حقيقية. شكل مفتاح الفاتورة ورقم التحقق حقيقيين. اللي محاكاة: الإرسال لـ SEFAZ، والـ CNPJ (لأن الداتا مخفية الهوية).

**س: ليه الطلبات القديمة متتعدلش؟**
ج: لأنها مصدر التحليل. لو اتعدلت، أرقام Modules 2–4 هتبقى غلط.

**س: لو طلب فيه بائعين؟**
ج: كل بائع بيطلع فاتورته، والطلب ميبقاش `invoiced` غير لما الاتنين يطلعوا.

**س: إزاي اتأكدتي إن الكود شغال؟**
ج: فيه 16 test (`backend/tests/`) بيشتغلوا على نسخة من الداتا الحقيقية في الميموري: رحلة الطلب كاملة، البوليتو، تعدد البائعين، ترقيم الفواتير، الإلغاء خلال 24 ساعة وبعدها، ورقم التحقق.

## 8. التشغيل

شوفي قسم **Run it** في الـ README. باختصار:
1. حطي الـ 9 ملفات CSV في `data/raw/`
2. `cd backend` ← اعملي venv ← `pip install -r requirements.txt` ← `python -m scripts.build_database` ← `uvicorn app.main:app --reload`
3. في terminal تاني: `cd frontend` ← `npm install` ← `npm run dev` ← افتحي http://localhost:5173

جربي السيناريو ده: سجلي طلب لعميل من Rio فيه منتجين من بائعين مختلفين وادفعي بالكارت على 6 أقساط ← Start processing ← اعملي Issue NF-e للبائعين الاتنين ← افتحي الـ DANFE ← Hand over to carrier ← Confirm delivery.
